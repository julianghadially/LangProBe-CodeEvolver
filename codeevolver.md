## ARCHITECTURE TITLE: Multi-hop RAG pipeline (SimplifiedBaleen) over LoTTE-tech with HTTP-injected retriever, scored by RAG-QA Arena's bidirectional pairwise LFRQA win-rate judge

## ARCHITECTURE SUMMARY:
The entry point is `RAGQAArenaTechPipeline` (`RAGQAArenaTech_pipeline.py`), a thin dspy.Module wrapper that owns the LM (DeepSeek-V4-Flash via GMI Cloud, `reasoning_effort="high"`) and an injected `HTTPEmbeddingRetriever` client, then delegates each `forward(question)` call to an inner pure-logic program — by default `SimplifiedBaleen` (`RAGQAArenaTech_program.py`). The wrapper exists so CodeEvolver can swap or compose the inner program without touching the eval harness. Retrieval is decoupled from the process: `RAGQAArenaTech_retrieval.py` is a stateless HTTP client over a separate warm `ragqa-retriever-server` that holds the 3.7GB LoTTE-technology embedding index (`text-embedding-3-small`), exposed as a process-wide singleton via `get_default_retriever`.

`SimplifiedBaleen` performs `max_hops=2` multi-hop retrieval: each hop runs a `dspy.ChainOfThought(GenerateSearchQuery)` (`RAGQAArenaTech_utils.py`) over accumulated context + question, calls `retriever.search(query, k=5)`, deduplicates passages, then synthesizes a final answer via `dspy.ChainOfThought("context, question -> response")`. The retrieved passages are attached as `pred.context` so downstream faithfulness metrics can see the evidence.

The optimized metric, `ragqa_pairwise_winrate_feedback` (`metric.py:412`), is a faithful port of RAG-QA Arena's LFRQA pairwise judge (arXiv:2407.13998): a gpt-5.4-mini judge (temperature 0) sees the query, the system response, and the gold LFRQA "faithful_answer" (no passages), uses the verbatim system rubric + 3 in-context examples from `rqa_arena_eval/`, and emits `<rating>0|1|2</rating>`. A bidirectional double-poll (gold-first then system-first, mean of the two) cancels position bias; per-row score is win=1.0 / tie=0.5 / loss=0.0, returned as `ScoreWithFeedback` with the judge's one-line `<reason>` and directional optimizer guidance. The file also contains a SemanticF1 variant and a composite CFC (completeness/faithfulness/conciseness) metric, but the active optimization target is the pairwise win-rate.

## ARCHITECTURE DESCRIPTION:
`RAGQAArenaTechPipeline` (langProBe/RAGQAArenaTech/RAGQAArenaTech_pipeline.py:35) is the per-row entry point. It configures `dspy.LM("openai/deepseek-ai/DeepSeek-V4-Flash", api_base=GMI, reasoning_effort="high")`, disables DSPy's disk/memory cache so every eval exercises the real LM, constructs (or accepts) an `HTTPEmbeddingRetriever`, and instantiates `SimplifiedBaleen(retriever)` as the inner program. `forward(question)` wraps the call in `dspy.context(lm=self.lm)` and delegates to `self.program(question=question)`.

`SimplifiedBaleen` (RAGQAArenaTech_program.py:6) is a multi-hop RAG dspy.Module with `max_hops=2`, `num_docs=5`. Each hop: (1) `generate_query[hop]` (a `ChainOfThought(GenerateSearchQuery)`) produces a search query from context+question, (2) `self.search(query, k=5)` proxies to `retriever.search`, (3) passages are appended and deduplicated (`langProBe.dspy_program.deduplicate`). After the hops, `self.respond` (`ChainOfThought("context, question -> response")`) synthesizes the answer, and `pred.context` is set to the accumulated passages for downstream faithfulness scoring. `GenerateSearchQuery` (RAGQAArenaTech_utils.py:4) is the dspy.Signature driving query generation.

`HTTPEmbeddingRetriever` (RAGQAArenaTech_retrieval.py:76) is a thin, thread-safe, connection-pooled client over a separate warm local server (`RAGQA_RETRIEVER_URL`, default `http://localhost:8894/api/search`) that owns the 3.7GB LoTTE-tech `index.pt`. `search(query, k)` GETs the endpoint, returns the top-k passage texts (truncated to 4000 chars), records per-doc scores on the active OTel span, retries on timeout/connection errors, and is shared as a process-wide singleton via `get_default_retriever` (double-checked-locked). `__deepcopy__`/`__copy__` return `self` so the optimizer never clones retrieval infrastructure. Tracing is wired through `_tracing.py`/`tracing_setup.py` (OpenInference/DSPy→OTel spans).

The optimized metric `ragqa_pairwise_winrate_feedback` (metric.py:412) implements RAG-QA Arena's model-based pairwise evaluation (arXiv:2407.13998). It runs two judge polls (gpt-5.4-mini, temp 0) per row — gold LFRQA answer in slot 1 then in slot 2 — using the verbatim system prompt and 3 ICL examples vendored under `rqa_arena_eval/` (`pairwise_lfrqa_system.txt`, `pairwise_lfrqa_examples.json`) and a rendered `pairwise_lfrqa.cfg`-style template asking for `<reason>` and `<rating>0|1|2</rating>`. Each poll's rating is mapped through the slot order to win/tie/loss for the system answer (1.0/0.5/0.0); the row score is the mean of the two polls (cancelling position bias). It returns `dspy.teleprompt.gepa.ScoreWithFeedback(score, feedback)` where feedback carries the outcome, both poll ratings, the judge's one-line reasons (visible `<reason>` tag, with `reasoning_content` fallback), and directional guidance (loss → improve factual grounding/coverage; tie → add truthful query-relevant coverage; win → preserve). `ragqa_pairwise_outcome`/`ragqa_pairwise_winrate` expose raw win/tie/loss and a plain scalar for non-CodeEvolver callers. The file additionally defines `ragqa_semantic_f1_feedback` (LLM-judge key-idea recall/precision F1) and `ragqa_cfc_feedback` (weighted completeness 0.5 + faithfulness 0.25 + conciseness 0.25), but the active optimization target is the pairwise win-rate feedback metric.
