## ARCHITECTURE SUMMARY:
RAGQAArenaTech is a DSPy-based multi-hop RAG question-answering benchmark over the LoTTE "technology" corpus. The architecture separates concerns into three layers: a thin pipeline wrapper (`RAGQAArenaTech_pipeline.py`) that owns LM configuration and the retrieval database; a pure-logic inner program (`RAGQAArenaTech_program.py::SimplifiedBaleen`) that performs iterative query-generation, passage search, and answer synthesis; and an out-of-process dense-retrieval server fronted by a pooled HTTP client (`RAGQAArenaTech_retrieval.py`). This separation lets the CodeEvolver IterationArchitect evolve the inner program (hops, query prompts, answer synthesis) without touching IO or the evaluation harness.

Scoring is implemented in `metric.py`, which exposes three metric families: the original SemanticF1, a faithful reproduction of RAG-QA Arena's pairwise LFRQA model-based win-rate metric (the one being optimized here), and a composite Completeness/Faithfulness/Conciseness (CFC) metric. The optimized metric, `ragqa_pairwise_winrate_feedback`, runs a single GPT-5.4-mini judge per row comparing the system answer against the human LFRQA "faithful_answer", with deterministic position assignment, and returns a `ScoreWithFeedback` carrying win/tie/loss plus directional optimization guidance.
## ARCHITECTURE DESCRIPTION:
The entry point is `RAGQAArenaTechPipeline` in `langProBe/RAGQAArenaTech/RAGQAArenaTech_pipeline.py`. It is a `dspy.Module` subclass that owns the generator LM (DeepSeek-V4-Flash via GMI Cloud, with `reasoning_effort="high"`), disables DSPy's disk/memory caches to ensure representative evals, and constructs a singleton `HTTPEmbeddingRetriever`. The retriever is injected into the inner program `SimplifiedBaleen` (`RAGQAArenaTech_program.py`), keeping the program pure logic. The pipeline's `forward(question)` simply activates the LM context and delegates to the inner program.

`SimplifiedBaleen` performs `max_hops=2` iterations: each hop runs a `dspy.ChainOfThought(GenerateSearchQuery)` (signature defined in `RAGQAArenaTech_utils.py`) over the accumulating `context` and `question`, calls `retriever.search(query, k=5)`, and deduplicates passages via `langProBe.dspy_program.deduplicate`. After hops, a `dspy.ChainOfThought("context, question -> response")` synthesizes the final answer. Critically, the retrieved passages are attached to the prediction as `pred.context` so downstream faithfulness metrics can inspect the evidence.

Retrieval (`RAGQAArenaTech_retrieval.py`) is a thin, thread-safe HTTP client over a separate warm `ragqa-retriever-server` process that holds the 3.7GB embedding index (OpenAI text-embedding-3-small) loaded once at boot. A shared `requests.Session` with a connection pool (pool_maxsize=32) handles concurrent calls from `dspy.Evaluate`. The client supports retries, a 4000-char truncation per passage, and is treated as a non-copying singleton by the optimizer.

The metric being optimized, `ragqa_pairwise_winrate_feedback` in `metric.py`, faithfully reproduces the RAG-QA Arena pairwise LFRQA evaluation (arXiv:2407.13998). It uses a `PAIRWISE_JUDGE_LM = "openai/gpt-5.4-mini"` judge at temperature 0, renders a verbatim template (query + two answers, no passages), prefixes the verbatim system rubric and three in-context examples from `rqa_arena_eval/`, assigns the system vs. gold answer to slot 1/2 deterministically by query word-count parity, parses `<rating>0|1|2</rating>`, and maps the outcome to win=1.0/tie=0.5/loss=0.0. The feedback variant wraps this in a `ScoreWithFeedback` exposing the judge's one-line `<reason>` plus directional guidance (improve grounding/coverage for losses, add truthful coverage for ties, preserve for wins). The metric file also hosts the legacy SemanticF1 and the composite CFC metrics, all sharing the same judge LM and CodeEvolver `(output, example, ...)` contract that reads gold fields off the dspy.Example row.
