## ARCHITECTURE TITLE: Multi-hop RAG over LoTTE-tech with HTTP-served dense retrieval, judged by a bidirectional pairwise LLM win-rate metric
## ARCHITECTURE SUMMARY:
RAGQAArenaTechPipeline (langProBe/RAGQAArenaTech/RAGQAArenaTech_pipeline.py) is a thin DSPy Module wrapper that owns LM configuration (DeepSeek-V4-Flash via GMI Cloud/LiteLLM, reasoning_effort="high") and an injected retriever, then delegates per-question execution to an inner pure-logic program — by default SimplifiedBaleen (RAGQAArenaTech_program.py). Retrieval is served out-of-process by a warm local server ("ragqa-retriever-server") over a 3.7GB precomputed embedding index; the in-process client HTTPEmbeddingRetriever (RAGQAArenaTech_retrieval.py) is a connection-pooled singleton that preserves the original `search(query, k) -> list[str]` interface so the program does no IO. The optimized metric, `ragqa_pairwise_winrate_feedback` (metric.py), is the RAG-QA Arena paper's model-based pairwise win-rate (vs. the human LFRQA "faithful answer"), run bidirectionally and returned as a `ScoreWithFeedback` for CodeEvolver/GEPA reflection.

## ARCHITECTURE DESCRIPTION:
Entry point `RAGQAArenaTechPipeline` (langProBe/RAGQAArenaTech/RAGQAArenaTech_pipeline.py:35) subclasses `LangProBeDSPyMetaProgram` + `dspy.Module`. Its `__init__` builds a `dspy.LM` (DeepSeek-V4-Flash via GMI Cloud, reasoning_effort=high), acquires the default retriever via `get_default_retriever()`, and instantiates the inner program `SimplifiedBaleen(retriever)` (RAGQAArenaTech_program.py:6). `forward(question)` simply opens a `dspy.context(lm=self.lm)` block and calls `self.program(question=question)`, returning the program's `dspy.Prediction` (which carries `.response` and `.context`).

`SimplifiedBaleen` (RAGQAArenaTech_program.py:6) is the multi-hop RAG core: for `max_hops=2` it iterates a per-hop `dspy.ChainOfThought(GenerateSearchQuery)` (the signature in RAGQAArenaTech_utils.py:4, fields context/question/query), retrieves `num_docs=5` passages per hop via the injected retriever's `.search(query, k)`, deduplicates accumulated context (langProBe.dspy_program.deduplicate), then synthesizes a final `response` with `dspy.ChainOfThought("context, question -> response")`. Critically it attaches the retrieved passage list to `pred.context` so downstream faithfulness metrics can see the evidence.

`HTTPEmbeddingRetriever` (RAGQAArenaTech_retrieval.py:43) is a stateless client over a single module-level `requests.Session` (HTTPS adapters, pool_maxsize=32) calling `GET {RAGQA_RETRIEVER_URL}/api/search?query=..&k=..` (default localhost:8894), with retry/backoff and `max_characters=4000` truncation per passage. `get_default_retriever()` (:114) builds it once under double-checked locking; `__deepcopy__`/`__copy__` return `self` so the optimizer never clones retrieval infra. Server-side offline index lives in the separate `ragqa-retriever-server` repo.

The optimized metric `ragqa_pairwise_winrate_feedback` (metric.py:412) reproduces AWS's RAG-QA Arena pairwise LFRQA evaluation (arXiv:2407.13998). Per row it runs a bidirectional poll: gold LFRQA answer vs. system answer in both slot orders, scored win=1.0/tie=0.5/loss=0.0 and averaged → {0,.25,.5,.75,1}. The judge is `openai/gpt-5.4-mini` at temperature 0, given a verbatim system prompt + 3 in-context examples (rqa_arena_eval/ assets) plus a templatized user turn ending in `<reason>…</reason><rating>0|1|2</rating>`. `_parse_rating` extracts the rating; `_majority_rating` aggregates N votes (default 1). The metric returns a `dspy.teleprompt.gepa.ScoreWithFeedback` whose `feedback` string includes the score, both poll ratings, the question/gold/system response, the judge's extracted short reason, and directional optimizer guidance keyed off the outcome (win/tie/loss) emphasizing truthful, grounded coverage. Sibling metrics in the same file (SemanticF1-feedback and the composite Completeness/Faithfulness/Conciseness CFC metric) follow the same `ScoreWithFeedback` contract but are not the one being optimized here. The `__init__.py` benchmark registry additionally lists several non-RAG baselines (Predict, CoT, GeneratorCritic*) for reference but the CodeEvolver entry point is the pipeline wrapper above.
