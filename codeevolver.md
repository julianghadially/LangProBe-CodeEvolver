## ARCHITECTURE TITLE: HoverMultiHopPipeline — 3-Hop DSPy Retrieve-Summarize-Query Claim Verification with ColBERTv2 + CountingRM

## ARCHITECTURE SUMMARY:
The system is a DSPy multi-hop fact-checking pipeline for the HoVer benchmark that verifies claims by iteratively retrieving Wikipedia passages via a remote ColBERTv2 server. `HoverMultiHopPipeline` (`hover_pipeline.py`) is the entry wrapper that wires up the LLM (DeepSeek-V4-Flash via GMI Cloud), a thread-safe `CountingRM` retrieval wrapper (`counting_rm.py`), and delegates the actual reasoning to `HoverMultiHop` (`hover_program.py`). The inner program performs three retrieve-then-summarize hops, accumulating up to 21 passages. The metric (`hover_utils.py`) scores whether all gold supporting documents appear in the returned set, penalized by the number of ColBERT searches beyond a 2-search free budget, and returns a `ScoreWithFeedback` for reflective optimization.

## ARCHITECTURE DESCRIPTION:
`HoverMultiHopPipeline` (langProBe/hover/hover_pipeline.py:28) is a thin `LangProBeDSPyMetaProgram`/`dspy.Module` wrapper invoked once per evaluation row with `forward(claim)`. It constructs a `dspy.LM` pointed at DeepSeek-V4-Flash through GMI Cloud (with `reasoning_effort="high"`), wraps `dspy.ColBERTv2(url=...)` in `CountingRM`, and instantiates `HoverMultiHop` as `self.program`. On each `forward` it resets the retrieval counter, enters `dspy.context(lm, rm)`, calls `self.program(claim=claim)`, and attaches `result.search_count = self.rm.get_count()` before returning. Importing the module also disables DSPy caching and runs `tracing_setup.py`, which installs the OpenInference DSPyInstrumentor so every Predict/ChainOfThought/Retrieve/LM call emits an OTel span (context propagated across DSPy's thread pool).

`HoverMultiHop` (langProBe/hover/hover_program.py:5) implements the fixed 3-hop logic with `k=7` retrievals per hop: (1) retrieve on the raw claim and summarize the 7 passages; (2) generate a refined query from `claim + summary_1`, retrieve 7 passages, and summarize using `claim + summary_1 + hop2 passages`; (3) generate a third query from `claim + summary_1 + summary_2`, retrieve 7 more passages, and concatenate all hop1+hop2+hop3 passages (≤21) into `dspy.Prediction(retrieved_docs=...)`. Summaries use `dspy.ChainOfThought` and queries are generated by two CoTHop modules.

`CountingRM` (langProBe/hover/counting_rm.py:25) wraps the ColBERTv2 retriever. It uses a module-shared `requests.Session` with a 32-connection/100-max pool (avoids per-call DNS churn under concurrency), monkey-patches `colbertv2_get_request_v2`/`colbertv2_get_request` to use a pooled GET with a 240s timeout, retries transient Timeout/ConnectionError twice with 60s backoff, and tracks per-thread invocation counts via `threading.local()` so parallel `dspy.Evaluate` threads keep independent counters.

`hover_utils.discrete_retrieval_eval_with_resource_penalty_and_feedback` (langProBe/hover/hover_utils.py:69) is the optimized metric. It normalizes the gold titles from `example["supporting_facts"]`, normalizes the top-21 predicted titles (split on ` | `), and computes `success = float(gold ⊆ found)`. It reads `pred.search_count`, computes `penalty = 0.002 * max(0, search_count - 2)` (2 free searches, no hard cap on searches), and returns `ScoreWithFeedback(score=max(0, success-penalty), feedback=...)` where feedback details missing documents, the cap of 21 docs, and the penalty breakdown for GEPA-style reflective optimization. The only hard constraint (MAX_RETRIEVED_DOCS=21) is enforced in the metric by slicing `pred.retrieved_docs[:21]`. Data comes from `hoverBench` (hover_data.py) which loads the `hover-nlp/hover` HF dataset, filters to claims with ≤3 unique supporting documents (3-hop examples), and shuffles with fixed seeds.
