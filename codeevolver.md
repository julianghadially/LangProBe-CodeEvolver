## ARCHITECTURE TITLE: 5-Hop Entity-Focused Retrieval with Verbatim Seed Filtering, Duplicate-Detection Fallback, Claim Decomposition Pre-Step, Post-Hop4 Summarization (Summarize3), Gap Analysis, and Round-Robin Interleaving (k=22)

## ARCHITECTURE SUMMARY:
`HoverMultiHopPipeline` (`langProBe/hover/hover_pipeline.py`) is the evaluator-facing entry point. It wires together an LM (`openai/gpt-5.4-nano`, reasoning_effort="low"), a `CountingRM`-wrapped ColBERTv2 retriever, and the core `HoverMultiHop` program, then tags each prediction with the search count for downstream metric use.

`HoverMultiHop` (`langProBe/hover/hover_program.py`) implements a 5-hop entity-focused retrieval loop with a claim decomposition pre-step and two code-level query guards. Before hop 1, `ClaimEntityExtractSignature` (LM only, no retrieval) extracts 2-4 canonical Wikipedia article titles for entities named verbatim in the claim. These seeds are immediately filtered by `_filter_seeds_verbatim`, which discards any seed whose text does not appear as a case-insensitive substring in the claim (preventing hallucinated seeds like "Stuart Little" for an Ice Princess claim from steering hop4 off-track). Only `key_entities_filtered` is injected into hop4's and hop5's `summary` inputs. After each LM call for hop4 and hop5, `_is_near_duplicate` checks whether the generated query is an exact or substring match to any prior query; if so, `_get_seed_fallback` replaces it with the first filtered seed entity not yet in the retrieved titles. Each hop uses a dedicated `dspy.Signature` with explicit instructions to identify and query for specific named entities. Retrieval uses k=22 per hop for broader coverage. Summarization uses `Summarize1Signature` (after hop 1), `Summarize2Signature` (after hop 2), and `Summarize3Signature` (after hop 4). All results are merged via round-robin interleaving (`_interleave_and_deduplicate`) with a "20+1" merge strategy: the first 20 docs come from the 4-hop round-robin, and hop5's top new result occupies the 21st slot.

The metric (`langProBe/hover/hover_utils.py`) scores predictions as retrieval success (all gold supporting-document titles found within the hard cap of 21 returned docs) minus a soft penalty for search queries beyond a 2-query free budget (0.002 per extra search), returning a `ScoreWithFeedback` object for reflective optimization.

## ARCHITECTURE DESCRIPTION:
**What the program does:** Given a factual claim (from the HoVer multi-hop fact-verification dataset), the pipeline must retrieve all documents that constitute the supporting evidence. The dataset is pre-filtered to examples requiring exactly 3 unique supporting documents (`hover_data.py` filters for `count_unique_docs == 3` in train, `<= 3` in test).

**Data flow:**
1. The evaluator calls `HoverMultiHopPipeline.forward(claim=...)`.
2. `CountingRM` is reset; the pipeline runs `HoverMultiHop` under a `dspy.context` binding the configured LM and counting RM.
3. **Pre-step (Claim Decomposition)** — `ChainOfThought(ClaimEntityExtractSignature)` extracts 2-4 canonical Wikipedia article titles for entities named verbatim in the claim (LM only, no ColBERT call, search_count unaffected). The raw `key_entities` string is immediately passed through `_filter_seeds_verbatim`, which retains only those seeds whose text appears as a case-insensitive substring in the claim text. The result, `key_entities_filtered`, is used for all subsequent seed injection and fallback logic.
4. **Hop 1** — `dspy.Retrieve(k=22)` is called with the raw claim, yielding 22 passages. `ChainOfThought(Summarize1Signature)` produces `summary_1`, explicitly identifying which named entities from the claim were found and which are still missing.
5. **Hop 2** — `ChainOfThought(QueryHop2Signature)` generates an entity-focused query targeting a named entity from the claim not yet found; another `dspy.Retrieve(k=22)` fetches 22 more passages. `ChainOfThought(Summarize2Signature)` produces `summary_2`, building on `summary_1` to track remaining missing entities.
6. **Hop 3** — `ChainOfThought(QueryHop3Signature)` generates a third entity-focused query identifying the remaining uncovered entity from the claim; a third `dspy.Retrieve(k=22)` adds 22 more passages.
7. **Hop 4 (Gap Analysis)** — `_interleave_and_deduplicate` is called on hops 1-3 (max_docs=30) to produce a balanced title list; the top 20 titles are fed to `ChainOfThought(QueryHop4GapSignature)`. Its `summary` input is `summary_2` enriched with `key_entities_filtered` hints (only seeds confirmed verbatim in the claim), or plain `summary_2` if no seeds survived filtering. After the LM call, `_is_near_duplicate` checks the generated `hop4_query` against all prior queries; if a duplicate is detected, `_get_seed_fallback` substitutes the first filtered seed not yet in retrieved titles. A fourth `dspy.Retrieve(k=22)` fetches 22 more passages.
8. **Post-hop4 Summarization** — `ChainOfThought(Summarize3Signature)` produces `summary_3` by scanning hop4's passages for newly-named entities (persons, works, organizations, places referenced with phrases like "founded by X" or "directed by X") that lack their own Wikipedia article in the retrieved set.
9. **Hop 5 (Final Recovery)** — `_interleave_and_deduplicate` across all four hops (max_docs=21) produces the preliminary top-21. `ChainOfThought(QueryHop5FinalSignature)` receives a combined summary (`summary_2 + summary_3`) enriched with `key_entities_filtered` hints (or plain combined summary if no seeds pass the verbatim filter). After the LM call, `_is_near_duplicate` checks `hop5_query` against all prior queries; if a duplicate is detected, `_get_seed_fallback` substitutes the first filtered seed not yet in preliminary titles. A fifth `dspy.Retrieve(k=22)` fetches 22 more passages.
10. **20+1 Merge** — The first 20 docs from the preliminary 4-hop round-robin are kept unchanged; hop5's top new (non-duplicate) result is inserted as the 21st slot. If hop5 adds no new document, the natural 4-hop 21st slot is used as fallback.
11. `search_count` (5, one per hop) is attached from `CountingRM.get_count()`.

**Key modules and responsibilities:**
- `hover_pipeline.py` — `HoverMultiHopPipeline`: top-level pipeline; owns LM/RM instantiation, DSPy context scoping, and `search_count` attachment. Uses `MODEL = "openai/gpt-5.4-nano"`.
- `hover_program.py` — `HoverMultiHop`: 5-hop entity-focused ChainOfThought + Retrieve logic with a claim decomposition pre-step, verbatim seed filtering, duplicate-detection query fallback, and round-robin interleaving deduplication. Contains `ClaimEntityExtractSignature` (pre-hop LM-only entity seed extraction), `Summarize1Signature`, `Summarize2Signature`, and `Summarize3Signature` (entity-gap-aware summarization after hops 1, 2, and 4 respectively), plus `QueryHop2Signature`, `QueryHop3Signature`, `QueryHop4GapSignature`, and `QueryHop5FinalSignature`. Three helper methods implement the new guards: `_filter_seeds_verbatim` (discards LM-hallucinated seeds), `_is_near_duplicate` (detects repeated queries), and `_get_seed_fallback` (provides a fresh seed-entity query when a duplicate is detected).
- `counting_rm.py` — `CountingRM`: thread-safe (threading.local) wrapper around `dspy.ColBERTv2` targeting a remote Modal ColBERT endpoint. Monkey-patches ColBERT's HTTP layer to use a shared connection-pooled `requests.Session` with 60s timeout and 2 retries.
- `hover_utils.py` — metric functions: `discrete_retrieval_eval` (binary subset check), `discrete_retrieval_eval_with_resource_penalty` (float), and the primary `discrete_retrieval_eval_with_resource_penalty_and_feedback` (returns `ScoreWithFeedback`).
- `hover_data.py` — `hoverBench`: loads `hover-nlp/hover` from HuggingFace, filters 3-hop examples, wraps in `dspy.Example` with `claim` as the sole input field.
- `tracing_setup.py` — imports `DSPyInstrumentor` on module load to emit OTel spans for all DSPy calls.
- `langProBe/dspy_program.py` — `LangProBeDSPyMetaProgram`: shared base class providing `setup_lm` and `program_type`.

**Metric detail:** `discrete_retrieval_eval_with_resource_penalty_and_feedback(output, supporting_facts, ...)` checks whether the normalized titles of all gold `supporting_facts` are a subset of the normalized titles extracted from `pred.retrieved_docs[:21]`. Success is 1.0 or 0.0. A penalty of `0.002 * max(0, search_count - 2)` is subtracted (2 free searches; with 5 hops the penalty is 0.006). The result is a `ScoreWithFeedback` with `score` (composite float in [0,1]) and a textual `feedback` string listing missing documents and search statistics, enabling reflective/GEPA-style optimization.
