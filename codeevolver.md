## ARCHITECTURE TITLE: Three-Hop DSPy Retrieval Pipeline with CountingRM and Resource-Penalized Feedback Metric
## ARCHITECTURE SUMMARY:
The system is a DSPy-based multi-hop fact-checking retrieval pipeline for the HoVer benchmark. `HoverMultiHopPipeline` (hover_pipeline.py) is the top-level wrapper invoked per row: it wires a GMI-served DeepSeek-V4-Flash LM, a remote ColBERTv2 retriever wrapped in `CountingRM`, and delegates to the `HoverMultiHop` program (hover_program.py) which performs three sequential retrieve-then-summarize hops over a claim. The pipeline attaches `search_count` from the thread-local `CountingRM` to the prediction before returning, so the metric can penalize retrieval effort.

Supporting modules include `hover_data.py` (`hoverBench`) which loads the HoVer dataset filtered to ≤3-hop examples, `hover_utils.py` which holds the evaluation metric and penalty constants, `counting_rm.py` which counts retrievals per-thread and hardens ColBERT HTTP calls with a pooled session/timeout/retry patch, and `tracing_setup.py` which enables OpenTelemetry spans for DSPy calls.
## ARCHITECTURE DESCRIPTION:
`HoverMultiHopPipeline` (langProBe/hover/hover_pipeline.py:28) is the per-row entry point. Its `__init__` constructs a `dspy.LM` pointing at GMI Cloud's DeepSeek-V4-Flash with `reasoning_effort="high"`, a `CountingRM` wrapping `dspy.ColBERTv2` against a Modal-hosted ColBERT server, and an inner `HoverMultiHop` program. `forward(claim)` resets the retrieval counter, runs the program under `dspy.context(lm, rm)`, and copies `rm.get_count()` onto `result.search_count`.

`HoverMultiHop` (langProBe/hover/hover_program.py:5) implements the retrieval logic: hop 1 retrieves `k=7` passages directly from the claim and summarizes them; hop 2 generates a refined query from `claim + summary_1`, retrieves 7 more passages, and summarizes with prior context; hop 3 generates a query from `claim + summary_1 + summary_2` and retrieves 7 more passages. The three hop passage lists are concatenated into `retrieved_docs` (21 docs max, matching the hard cap).

`CountingRM` (langProBe/hover/counting_rm.py:25) is a thread-safe wrapper using `threading.local` so each evaluation thread tracks its own query count independently (required for `dspy.Evaluate` with `num_threads>1`). It also monkey-patches `dspy.dsp.colbertv2.colbertv2_get_request*` to use a shared connection-pooled `requests.Session` (pool_maxsize=100) with a 240s timeout and retries, fixing DNS/connection failures observed under concurrent load.

The metric `discrete_retrieval_eval_with_resource_penalty_and_feedback` (langProBe/hover/hover_utils.py:69) reads gold titles from `example.supporting_facts`, normalizes them, and checks that all gold titles appear in the top-21 of `pred.retrieved_docs` (titles extracted by splitting `" | "`). Success is 1.0 only if `gold_titles.issubset(found_titles)`. A soft resource penalty of `PENALTY_PER_SEARCH=0.002` is applied per search beyond a `FREE_SEARCH_BUDGET=2`, subtracted from success and floored at 0.0 — there is no hard cap on searches, only a soft cost trade-off. The metric returns a `ScoreWithFeedback` whose textual feedback reports success/missing docs, retrieved count, searches used, penalty, and composite score, giving reflective optimizers (e.g., GEPA) actionable signal to trade retrieval effort against accuracy. Dataset loading in `hoverBench` (langProBe/hover/hover_data.py:9) pulls the `hover-nlp/hover` HF dataset, filters train to exactly 3-hop examples and test to ≤3-hop, shuffles with fixed seeds, and wraps rows as `dspy.Example(...).with_inputs("claim")`.
